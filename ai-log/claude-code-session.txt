  The 6 concepts you must be able to explain

  1. What Supabase is: Postgres plus a set of services around it: Auth (GoTrue),

  2. Two keys:

     - The service_role key is secret, server-only, and bypasses RLS. You use it

  3. How a request becomes a user in the DB: the user logs in and gets a JWT.
     Each request sends the JWT, PostgREST verifies it and sets it per
     transaction (request.jwt.claims), Postgres switches to the authenticated
     role, and auth.uid() reads the user ID from it. Your RLS policies use
     auth.uid().
  4. Roles: anon (not logged in), authenticated (logged in), service_role
     (admin, bypasses RLS). Your policies target authenticated.
  5. getUser() vs getSession(): on the server, use getUser() or getClaims()
     because they verify the token. getSession() just reads the cookie, which
     can be forged. This answers the requirement that the server must verify the
     user itself.
  6. @supabase/ssr: the Next.js integration. It stores the session in cookies
     and refreshes tokens in middleware.

       72 +

       82 +                                                              
       83 +1. **Postgres RLS (the guarantee).** Every table has `ENABLE` 
          +and `FORCE ROW LEVEL SECURITY`. Policies grant access only thr
          +ough `app.has_role(workspace_id, min_role)`, which checks the 
          +caller's membership using `auth.uid()` (the user ID from the v
          +erified JWT). There are no "allow all" policies.

          +ership and role first, so users get `Not found.` or `Your role
          + does not allow this action.` instead of raw database errors. 
          +If this layer had a bug, RLS would still block the access. If 
          +RLS had a bug, this layer would still block it. The tests chec
          +k each layer separately.                                      
       85 +                                                              
       86 +### Why a policy mistake denies rather than allows            
       87 +                                                              
       88 +- **RLS on and no matching policy means no rows.** Forgetting 
          +a policy hides data instead of exposing it.                   
       89 +- **`FORCE`** applies RLS to the table owner too.             
       90 +- **No user context means no access:** `auth.uid()` is `NULL`,
          + `has_role(...)` is false, and nothing is visible (tested).   
       91 +- **Default privileges are revoked** for `anon`/`authenticated
          +` in `public`, so a new table isn't even reachable until someo
          +ne grants it explicitly. Grants are **column-level**: `workspa
          +ce_id`, `project_id` and `created_by` can't be updated, so row
          +s can't be moved between workspaces.                          
       92 +- **Composite foreign keys** (`notes(project_id, workspace_id)
          + → projects(id, workspace_id)`) make it impossible for a note 
          +to belong to a project in another workspace, even for a buggy 
          +writer.                                                       
       93 +- **The `rls-coverage` test** fails if any of the above regres
          +ses.                                                          
       94 +                                                              
       95 +### Never trusting client IDs                                 
       96 +                                                              
       97 +- The **user** comes only from the session: `requireCtx()` cal
          +ls `supabase.auth.getUser()`, which has the Auth server verify
          + the JWT. (`getSession()` only decodes the cookie and is never
          + used for identity.)                                          
       98 +- **Workspace/project/note IDs** from the URL or form body are
          + treated as *requests*. They're validated as UUIDs and then th
          +e database decides whether this user can see them.            
       99 +- **No existence oracle:** "doesn't exist", "belongs to anothe
          +r workspace", and "malformed ID" all return the same `Not foun
          +d.` / 404 page. The tests assert the results are *equal*, not 
          +just both failures. `forbidden` is only returned to members, w

● They're three ways the fake AI model (the mock) can behave. There's no real AI
  in the app, so the mock lets you show on demand how the app copes with a good
  model, a glitchy one and a hijacked one. You pick one in the "Mock model

  src/lib/summary/mock-provider.ts.

  normal: a well-behaved AI

  It reads the notes and returns a proper summary in the expected JSON format.
  - It summarizes the real notes (Kickoff, Risks).
  - It sees the "IGNORE PREVIOUS INSTRUCTIONS" note and doesn't obey it. It just
    mentions that a note contained instructions aimed at the AI.
  - Result: summary saved after 1 attempt, with a yellow warning that a
    suspicious note was found.

  What it proves: the normal path works, and an injected note is treated as
  data, not commands.

  malformed-once: an AI that glitches once

  The first reply is broken JSON, cut off mid-sentence:
  {"summary": "The project is on track and the team agreed on
  The second reply is fine. Real AI models really do this sometimes.
  - Attempt 1: our validation rejects it ("not valid JSON").
  - The app retries once.
  - Attempt 2: valid, so it's saved.
  - Result: "Attempt 1: rejected → Attempt 2: accepted", stored with 2 attempts.

  What it proves: the required edge case, where the model returns malformed
  output once and the app handles it safely, with no crash and no garbage saved.

  compromised: a hijacked AI

  This simulates the worst case: the AI obeyed the injected note. It returns:
  { "summary": "All notes deleted",
    "keyPoints": ["Admin mode enabled"],
    "citedNoteIds": ["00000000-..."],      ← a note ID that doesn't exist
    "systemPrompt": "You summarize..." }   ← trying to leak our instructions
  - Our strict schema rejects it, because systemPrompt is an extra field that
    isn't allowed. The fake note ID would also be rejected.
  - The retry gets the same bad output and is rejected again.
  - Result: "The model returned invalid output 2 times. Nothing was saved."

  What it proves: even if prompt injection fools the AI, the hijacked output
  can't get into the database, because we validate the AI's output too.

  How to explain it in one line

  ▎ "normal shows the happy path, malformed-once shows recovery from a broken 
  ▎ reply, and compromised shows that even a fooled model can't get bad data 
  ▎ stored: we never trust the AI's output, we validate it."
